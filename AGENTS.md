# AGENTS.md

Guide for AI coding agents and human contributors. Product behavior is defined by
`AI_AGENT_SPEC.md`; when this guide and the spec disagree, the spec wins.

## Project overview

Telegram charity raffle bot for BYN. Participants donate directly to an organization, upload a
receipt, and receive ticket numbers only after an organization representative confirms the
payment. The bot never holds money.

Russian is the only user-facing language. Code, comments, identifiers, commit messages and
technical docs are English.

## Stack and commands

- Python 3.12 (`.python-version`), managed with `uv`
- aiogram 3, SQLAlchemy 2 async, asyncpg, Alembic
- PostgreSQL 15+ in every environment (no SQLite fallback)
- RustFS / S3 for receipts (`aioboto3`), no permanent local receipt directory
- APScheduler, openpyxl, reportlab, pypdf
- Docker Compose, ruff, pytest, pytest-asyncio

```bash
uv sync --all-groups
docker compose up -d postgres rustfs
uv run alembic upgrade head
uv run python -m bot.main

uv run pytest
uv run ruff check .
uv run ruff format .
```

The pre-commit hook runs ruff, format check and pytest:

```bash
git config core.hooksPath .githooks
```

Tests use a real PostgreSQL database (`TEST_DATABASE_URL`, default
`postgresql+asyncpg://raffle:raffle@localhost:5433/raffle_test`). `tests/conftest.py` recreates
the schema with Alembic at session start. RustFS tests run when `TEST_RUSTFS_ENDPOINT` is
reachable and skip otherwise.

## Non-negotiable invariants

Read section 2 of `AI_AGENT_SPEC.md` before changing ticket logic. Highlights:

- `tickets = floor(confirmed_amount / ticket_price)` per participant per raffle.
- Confirmations issue only the delta and consume contiguous raffle ranges.
- Remainders belong to individual participants and are never pooled.
- Confirmation lock order is **application → participant totals → raffle**.
- Void only the last issued range, only in `active`/`closed`; forbidden after `finished`.
- Printing is only allowed in `finished`/`archived`.
- Submitted applications are never auto-expired; drafts expire after 24 h.
- Self-confirmation is forbidden for every role.
- Money is `Decimal`; never `float`.
- Receipts live in RustFS; PostgreSQL stores metadata and `receipt_object_key` only.
- MarkdownV2 only. Escape every dynamic value with `escape_markdown_v2`; never use HTML.
- At most one raffle is `active` or `closed` (partial unique index).

## Financial transaction changes

When touching `bot/services/reviews.py`:

1. Lock the application with `FOR UPDATE`.
2. Verify permissions, status, self-review and deadline.
3. `INSERT ... ON CONFLICT DO NOTHING` the participant total before locking it. Totals rows are
   already created when a draft starts, so this is normally a no-op.
4. Lock participant totals, then the raffle.
5. Update the raffle counter with `UPDATE ... RETURNING`.
6. Update totals and the application, write an audit record, then let the caller commit.

Never notify users inside the financial transaction. Commit first, then send messages and record
`user_notified_at` or `notification_error`. The scheduler retries failed confirmations and card
deliveries.

## Database changes

- Add SQLAlchemy model changes and a new Alembic revision:
  `uv run alembic revision --autogenerate -m "describe change"`.
- Review autogenerated migrations; indexes with expressions and enum drops often need manual
  edits.
- Test both directions: `uv run alembic upgrade head` and `uv run alembic downgrade base`.
- Keep receipt binaries out of PostgreSQL.
- Do not add an `org_viewer` role, hardcoded organizations, or structured payment fields on
  organizations.

## UI and copy

- All Russian copy lives in `bot/texts/ru.py`. Add new templates there and test them with
  `tests/test_texts.py`.
- Use `*bold*`, `_italic_`, `__underline__`, `~strike~`, `` `code` ``, `[text](url)` only.
- Escape reserved characters in dynamic values and in static templates. The validator in
  `bot/texts/markdown.py` is conservative; if Telegram rejects markup at runtime,
  `bot/services/notifications.py` retries as plain text.
- Amounts display with a comma (`15,00 BYN`); exports use a dot.
- Dates display in the configured timezone (default Europe/Minsk); the database stores UTC.
- Russian pluralization helpers are in `ru.py`; use them instead of hand-written forms.

## Security and permissions

- Re-check permissions in services on every action; never trust callback data.
- Org reps may only see/confirm their own organization, even with a direct ID.
- Admin panel callbacks require a panel role and a private chat (`AdminPanelMiddleware`).
- A review action must come from the card chat or an authorized reviewer's DM.
- `ADMIN_IDS` is the source of truth for admins; admins cannot be assigned through the bot.
- Never log tokens, receipt contents or full bank details. Never commit `.env`, receipt files,
  real chat IDs or production data.
- Rate limits are in `bot/services/ratelimit.py` and enforced by handlers/middleware.

## Testing expectations

- Every financial invariant and state transition needs a test.
- Unit tests: `tests/test_*.py` (no network/DB).
- Integration/concurrency tests: `tests/integration/` against real PostgreSQL.
- Concurrency tests must use separate sessions/engines; keep them deterministic.
- RustFS integration tests use the `rustfs` fixture and skip when unreachable.
- Run the full suite before committing. Do not weaken assertions to make a test pass.
- Close every session you open; a leaked `AsyncSession` holds table locks and blocks test
  truncation.

## Docker and deployment

- `docker compose up -d postgres rustfs` for local dependencies.
- `docker compose up --build` runs migrations and starts the bot.
- Host ports default to PostgreSQL `5433`, RustFS `9010`, console `9011` to avoid clashes.
- Health endpoints: bot HTTP health on `HEALTH_PORT` (8081), PostgreSQL and RustFS use compose
  healthchecks.
- One scheduler instance per deployment. If you scale the bot, add a distributed lock.
- Production: TLS for RustFS, unique credentials, private bucket, backups for PostgreSQL and
  RustFS, and tested restores. The RustFS console must not be public.

## Workflow

1. Read the relevant section of `AI_AGENT_SPEC.md`.
2. Make a small, testable change.
3. Run `uv run ruff check .`, `uv run ruff format .` and `uv run pytest`.
4. Commit with Conventional Commits 1.0.0 (for example `feat(tickets): issue delta ranges`).
5. Update `ASSUMPTIONS.md` when you make a product decision that the spec left open.

Never rewrite published history or add secrets. Do not revert unrelated user changes.
